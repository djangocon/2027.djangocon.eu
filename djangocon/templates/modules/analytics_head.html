{% comment %} Google Analytics 4, behind consent. Goes near the top of the document head, per Google's gtag.js install guide ("immediately after the opening head tag"), so that a returning visitor who has already accepted starts measuring as early as possible instead of waiting for the end of the body. There is deliberately no noscript fallback: that belongs to Google Tag Manager, whose noscript iframe still fires tags without JS. GA4's gtag.js measures purely in JavaScript, so a noscript block could not report anything and would be dead markup. The privacy guide tells visitors they can control non-essential cookies from a banner on first visit, and GDPR/ePrivacy require consent before analytics cookies are set. So gtag.js is not requested at all until the visitor accepts: no request reaches Google and no cookie is written on a first load or after a refusal. The banner itself is in modules/analytics_banner.html. The choice is kept in localStorage rather than a cookie -- it never needs to reach the server, and a cookie asking for consent to cookies is a poor look. Notes on the script below, kept here rather than inline because inline comments are served to the browser and show up in view-source: * read() swallows a localStorage failure (private mode, storage blocked) and returns null, i.e. undecided: the banner reappears next visit rather than the site tracking silently. * gtag is assigned to window because gtag.js looks it up there, and called through the local alias so the calls do not rely on an implicit global. * Traffic source, session duration and page-to-page navigation all come from GA4's own page_view and session handling, so none of those are measured by hand; the one custom event is the ticket-link click described below. * A previous "accept" is honoured on load, before the banner script runs. Ticket-link clicks are measured as a select_ticket_link event. Notes on that half, again kept out of the served markup: * The event is custom rather than GA4's begin_checkout because leaving for the shop is not a checkout step: the purchase happens on Pretix and we never learn whether it completed. Feeding it into the ecommerce funnel would invent a funnel we cannot close. Mark it as a key event in the GA4 UI if it should count as a conversion. * It is a delegated listener on the document rather than a handler per link, because ticket links appear in the header, the home hero, the ticket cards, navigation.json and the Markdown content. Matching on the shop host means a link added in content later is measured with no extra work. * closest('a') is what makes that work for a click landing on an element inside the link, and the host comparison covers any path on the shop. * Traffic source is deliberately not attached: GA4 resolves source, medium and campaign for the session itself, so the event inherits the attribution of the visit it belongs to. Only what GA4 cannot know is passed -- which page the click came from and where it went. * transport_type 'beacon' matters here: the click navigates away, and a normal request would be cancelled in flight. sendBeacon hands the hit to the browser, which delivers it after the page is gone. * Nothing is measured without consent, matching the promise in the privacy guide: no gtag means the listener returns before doing anything. {% endcomment %}
